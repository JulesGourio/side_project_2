## Working setup (read first)

Claude has no Databricks access from this machine: the code is pushed from here and deployed to Databricks from another machine, same as the sibling `transla` project. Never assume a deploy, job run or table change happened — every manual Databricks/UI step for the user (create table/index/volume, grants, deploy, job run, app.yaml value to switch) goes into `OPERATIONS.md`, ready to copy-paste, and is mentioned in chat. Keep `OPERATIONS.md` the single place for those steps; mark them done (dated) once the user confirms.

The code reaches the deploy machine as a zip. Git: commit and push straight to `main`, never open PRs.

## Parsing pipeline (`utils/parsing_pipeline/`, `resources/parsing_pipeline.job.yml`)

Daily chain: `1_categories` -> `2_manifest` -> `3_parse` (GPU) -> `4_describe_images` (LLM) -> `5_sync_index`. Schedule exists on all targets but is `PAUSED` until explicitly promoted.

- **Metadata source**: `prod_bronze.intraqual.gd_*_latest` (`config.INTRAQUAL_BRONZE_CATALOG_SCHEMA`), not `dev_bronze` — its stack stopped refreshing 2026-07-21. `00b` fails the run if any source table is stale (`PARSING_MAX_SOURCE_STALENESS_HOURS`).
- **Scope gate**: `config.DOC_SCOPE_FILTER` = `courant=1 AND etat=7 AND nonvisible=0` on `gd_doc_latest`. Replaced the old gate ("REF present in `intraqual_docs`", a manual portal scrape) on 2026-07-27 — that scrape is no longer read anywhere in the pipeline, but re-scraping live (`utils/deploy/scrap_ids_intraqual.py`) is still the way to validate the predicate against ground truth. `difftotale=1` was in the predicate initially but dropped 2026-07-28: a fresh live scrape showed `difftotale` doesn't mean "hidden from the portal" — 10 documents with `difftotale=0` were legitimately returned by the portal's default search and were being wrongly excluded.
- **Each Intraqual revision gets a brand-new IDDOC** — the same document's old IDDOC never gets its `indice`/`dtdiff` updated in place. Verified: REF `QR-1005` has 70 distinct IDDOCs (one per revision letter), only the latest `courant=1`; 3,666 REFs corpus-wide have more than one IDDOC. This means "detect a revision" is NOT "compare indice on the same IDDOC" — it's "the old IDDOC just drops out of scope, the new one appears".
- **Stale-content pruning**: `2_Cleanup_Volume.py` step 1b deletes `chunks`/`src_chunks_as`/`src_chunks_is`/`image_metadata`/`processed_files` rows for any previously-`SUCCESS` IDDOC no longer in scope (superseded revision or fully deleted from Intraqual — both look identical to the anti-join, both get pruned). Runs unconditionally, not gated by `DRY_RUN` (that widget only protects source *files* on the volume, not derived index rows). Added 2026-07-27 after finding ~200 stale IDDOCs / ~3,400 stale chunks accumulated under the old REF-based gate.
- **Cluster policies**: none of the org's 6 "Job Compute *" policies fit this job's clusters (all force `SPOT_WITH_FALLBACK`, which would reintroduce a fixed spot-driver-reclaim incident on the single-node CPU clusters; none allow a GPU-ML `spark_version`). Deliberate exception, no `policy_id` set — see the `databricks-job-conventions` skill for the audited policy list before revisiting.
- **`run_as`** (`job-runner-sa-uat`, `3e5cd4e5-f765-4760-b974-ee7715258b39`) — as of 2026-08-19, enabled and confirmed working end to end on: `parsing_pipeline` (`qualibot-uat` only — it isn't deployed on `qualibot-uat-test`, see the job's own YAML), `lakebase_export_uat_to_volume`, `apps_stop_nightly_uat`/`qualibot_stop_weekend_uat`/`qualibot_start_weekend_uat` (needed an explicit `CAN_MANAGE` app-permission grant, done 2026-08-19), and `migrate_lakebase_uat_test`/`sync_user_capabilities_uat_test`. The earlier Lakebase-Postgres-role blocker (`password authentication failed`) is resolved. Not usable in the `dev` target — this SP is UAT-workspace scoped; a `run_as` set there is silently ignored (job runs as the submitting user instead of erroring), confirmed live 2026-08-19.
