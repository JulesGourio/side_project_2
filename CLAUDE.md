MLflow traces of the chat (2026-10-12, DEV only for now, steps in `runbooks/dev.md` block Y): `server/services/chat/mlflow_turns.py` rebuilds each finished `TurnLog` as one MLflow trace (steps at their real offsets via `TurnLog.starts_ms`, passages sent as the retriever output, tokens/cost, issues, tags for the scorers) in the experiment named by `CHAT_MLFLOW_EXPERIMENT` (empty = off). UAT / prod: add `CHAT_MLFLOW_EXPERIMENT` to their `target_env.json` entries and their job blocks once DEV is validated. Evaluation assets (golden set, eval results, quality scores, prompt registry) live in `dev_proj.qualibot`.

  Names: the six parsing notebooks are `create_proj_<asset>.py` (`create_proj_category_reference`, `create_proj_parse_manifest`, `create_proj_chunks`, `create_proj_image_metadata`, `create_proj_doc_catalog`) and `update_proj_vector_indexes.py` (no table to create), without numbers: the order lives in the job YAML task chain (`1_categories` -> `6_update_kb_metadata`). ## Parsing pipeline (`utils/parsing_pipeline/`, `resources/parsing_pipeline.job.yml`)

Daily chain: `1_categories` -> `2_manifest` -> `3_parse` (GPU) -> `4_describe_images` (LLM) -> `5_sync_index`. Schedule exists on all targets but is `PAUSED` until explicitly promoted.

- **Metadata source**: `prod_bronze.intraqual.gd_*_latest` (`config.INTRAQUAL_BRONZE_CATALOG_SCHEMA`), not `dev_bronze` — its stack stopped refreshing 2026-07-21. `00b` fails the run if any source table is stale (`PARSING_MAX_SOURCE_STALENESS_HOURS`).
- **Scope gate**: `config.DOC_SCOPE_FILTER` = `courant=1 AND etat=7 AND nonvisible=0` on `gd_doc_latest`. Replaced the old gate ("REF present in `intraqual_docs`", a manual portal scrape) on 2026-07-27 — that scrape is no longer read anywhere in the pipeline, but the predicate is validated against the live portal by hand, outside this repository. `difftotale=1` was in the predicate initially but dropped 2026-07-28: a fresh live scrape showed `difftotale` doesn't mean "hidden from the portal" — 10 documents with `difftotale=0` were legitimately returned by the portal's default search and were being wrongly excluded.
- **Each Intraqual revision gets a brand-new IDDOC** — the same document's old IDDOC never gets its `indice`/`dtdiff` updated in place. Verified: REF `QR-1005` has 70 distinct IDDOCs (one per revision letter), only the latest `courant=1`; 3,666 REFs corpus-wide have more than one IDDOC. This means "detect a revision" is NOT "compare indice on the same IDDOC" — it's "the old IDDOC just drops out of scope, the new one appears".
- **Date cutoff routes, it no longer excludes** (2026-10-02): documents published before `DOC_DATE_CUTOFF` (2018-01-01) are parsed and described like the others, but `3_parse`/`4_describe_images` write their chunks to `chunks_archive`, never to `chunks` (chatbot). `5_sync_index` MERGEs `chunks` + `chunks_archive` into `chunks_full` (60-day retention, CDF) when `chunks_full_index` is in `parsing_vector_search_indexes`. `parsed_documents.is_filtered_by_date=True` now means "archive", not "not parsed".
- **Archive test phase** (2026-10-05, nothing switched on yet — see `runbooks/uat.md` block B/D): `parsing_archive_max_docs` caps the TOTAL number of pre-2018 documents parsed, most recent first (default `0` = none; `parse_manifest.parse_content` carries the decision). `3_parse` writes one metadata-only notice chunk per pre-2018 document to `archive_notices` on every run; they reach `chunks` only when `parsing_archive_notices_in_rag` is `true` (the matching chatbot rule, written for the KA, restorable from git commit `f545093` (`archive/knowledge_assistant/provisioning/ka_profiles.py`), must move to `server/prompts/chat/system/base.md` first — `runbooks/uat.md` D3). `chunks_full` is built on `qualibot-uat` (`parsing_build_chunks_full`) but `chunks_full_index` was removed from `parsing_vector_search_indexes`: the user wants to test before any index changes.
- **Stale-content pruning**: `create_proj_parse_manifest.py` step 1b (scope in `categories.py`) deletes `chunks`/`chunks_archive`/`image_metadata`/`parsed_documents` rows for any previously-`SUCCESS` IDDOC no longer in scope (superseded revision or fully deleted from Intraqual — both look identical to the anti-join, both get pruned). Runs unconditionally, not gated by `DRY_RUN` (that widget only protects source *files* on the volume, not derived index rows). Added 2026-07-27 after finding ~200 stale IDDOCs / ~3,400 stale chunks accumulated under the old REF-based gate.
- **Cluster policies**: the CPU clusters of `lakebase_sync` and of the parsing job use the CORE Job Compute S policy (`job_cluster_policy_id_S` per target, ids in `databricks.yml`; the same workspaces as `datab/templates/bundle_data_asset/`). ## Operational conventions (for Claude, not for the repository documentation)

These rules are for whoever changes the code. They do not belong in the READMEs or in the code comments.

- Notebooks under `utils/` (`*_job.py`, `ensure_*`, `import_*`, `grant_*`, `stop_start_app_job.py`, `evaluation/*.py` marked `# Databricks notebook source`) do not run from the command line. They are job tasks or notebooks opened in Databricks.
- Logging uses `logger` (the `logging` module), never `print`. Notebooks and command-line scripts follow the same rule.
- A notebook that takes parameters declares them as widgets, after `dbutils.widgets.removeAll()`.
- Notebooks import `ops_config.py` after adding `utils/` to `sys.path`: `sys.path.insert(0, os.path.dirname(os.getcwd()))` in notebooks (their folder is on `sys.path`, its parent is `utils/`), `Path(__file__).resolve().parent.parent` in command-line scripts.
- On data columns, `try_cast` and `try_to_date` replace `cast` and `to_date`, so one malformed value does not fail the whole task.
- `target_env.json` is the single source of the application settings per target. The PowerShell deploy script and the Bitbucket pipeline both read it: never copy its values elsewhere.
- Application start and stop (`app_mgmt/stop_start_app_job.py`): the SDK raises `BadRequest` when the application is already in the requested state. The notebook reads the state first and skips the call when it is already there.
- Line endings of the rendered `target_config.env`: `render_target_config_env.py` writes LF. A CRLF file adds a `\r` to every value, and every URL built from those values becomes wrong.
- A notebook imported into the workspace: `databricks workspace import` must target exactly the job's `notebook_path` (without the `.py` suffix), otherwise a duplicate appears without an error.
- Deployment: the application is deployed with `utils/deploy/deploy_qualibot.ps1` (or the Bitbucket pipeline), the jobs with `databricks bundle deploy`. The root README describes the targets.
- Job format: every job sets `queue`, `email_notifications` on `on_failure` with `${var.notification_email}`, `notification_settings.no_alert_for_canceled_runs`, and the tags `activity-type` (`${var.job_activity_tag}`), `job-purpose` and `project-name`. The template is `datab/templates/bundle_data_asset/`.
- `CAN_QUERY` is never granted on serving endpoints: every workspace user already queries them (`CLAUDE.md`, Databricks section).
- READMEs never mention `runbooks/` (no link, no index, no sentence pointing to the steps): the folder is temporary in this repository. Inside `runbooks/` itself, the usage commands keep the script paths, and `runbooks/README.md` is that folder's own index.
