## Code conventions (since 2026-10-08)

- **Comments**: only the non-obvious *why*, in one or two lines. No incident story, no date, no document or ticket name (the story goes in a README, the rule stays in the code), no paraphrase of the code, no commented-out code.
- **Logging**: `logger` in notebooks and modules, never `print`; CLI scripts under `utils/` follow the same rule.
- **Notebooks** (`utils/parsing_pipeline/`, `utils/generic_pipeline/`) follow the LEAP layout of `JulesGourio/datab` (`CLAUDE.md` there, sections 3-4 and 16): header cell, `Technical debt`, `Configuration`, `Inputs`, `Data Preparation` (`Prep N`), `Data Transformations` (`Tr. N`), `Quality Checks`, `Outputs`; a markdown cell with the *why* before each block; no `DBTITLE`. No Silver / Gold / `leap_utils` / GX here. Logic lives in modules next to the notebook (`parse_steps.py` for `3_parse`), the notebook only orchestrates.
- **Layout of `utils/`**: one folder per concern, map in `utils/README.md`.
- After a refactor that touches paths or notebooks, append what to re-run to `RETEST_CLEANUP.md`.

## Parsing pipeline (`utils/parsing_pipeline/`, `resources/parsing_pipeline.job.yml`)

Daily chain: `1_categories` -> `2_manifest` -> `3_parse` (GPU) -> `4_describe_images` (LLM) -> `5_sync_index`. Schedule exists on all targets but is `PAUSED` until explicitly promoted.

- **Metadata source**: `prod_bronze.intraqual.gd_*_latest` (`config.INTRAQUAL_BRONZE_CATALOG_SCHEMA`), not `dev_bronze` — its stack stopped refreshing 2026-07-21. `00b` fails the run if any source table is stale (`PARSING_MAX_SOURCE_STALENESS_HOURS`).
- **Scope gate**: `config.DOC_SCOPE_FILTER` = `courant=1 AND etat=7 AND nonvisible=0` on `gd_doc_latest`. Replaced the old gate ("REF present in `intraqual_docs`", a manual portal scrape) on 2026-07-27 — that scrape is no longer read anywhere in the pipeline, but re-scraping live (`utils/deploy/scrap_ids_intraqual.py`) is still the way to validate the predicate against ground truth. `difftotale=1` was in the predicate initially but dropped 2026-07-28: a fresh live scrape showed `difftotale` doesn't mean "hidden from the portal" — 10 documents with `difftotale=0` were legitimately returned by the portal's default search and were being wrongly excluded.
- **Each Intraqual revision gets a brand-new IDDOC** — the same document's old IDDOC never gets its `indice`/`dtdiff` updated in place. Verified: REF `QR-1005` has 70 distinct IDDOCs (one per revision letter), only the latest `courant=1`; 3,666 REFs corpus-wide have more than one IDDOC. This means "detect a revision" is NOT "compare indice on the same IDDOC" — it's "the old IDDOC just drops out of scope, the new one appears".
- **Date cutoff routes, it no longer excludes** (2026-10-02): documents published before `DOC_DATE_CUTOFF` (2018-01-01) are parsed and described like the others, but `3_parse`/`4_describe_images` write their chunks to `chunks_archive`, never to `chunks` (chatbot). `5_sync_index` MERGEs `chunks` + `chunks_archive` into `chunks_full` (60-day retention, CDF) when `chunks_full_index` is in `parsing_vector_search_indexes`. `processed_files.filtered_by_date=True` now means "archive", not "not parsed".
- **Archive test phase** (2026-10-05, nothing switched on yet — see `OPERATIONS.md` block B/D): `parsing_archive_max_docs` caps the TOTAL number of pre-2018 documents parsed, most recent first (default `0` = none; `parse_manifest.parse_content` carries the decision). `3_parse` writes one metadata-only notice chunk per pre-2018 document to `chunks_archive_notices` on every run; they reach `chunks` only when `parsing_archive_notices_in_rag` is `true` (the matching chatbot rule, written for the KA in `archive/knowledge_assistant/provisioning/ka_profiles.py`, must move to `server/config/chat_vsi/answer_rules.md` first — `OPERATIONS.md` D3). `chunks_full` is built on `qualibot-uat` (`parsing_build_chunks_full`) but `chunks_full_index` was removed from `parsing_vector_search_indexes`: the user wants to test before any index changes.
- **Stale-content pruning**: `2_Cleanup_Volume.py` step 1b deletes `chunks`/`chunks_archive`/`image_metadata`/`processed_files` rows for any previously-`SUCCESS` IDDOC no longer in scope (superseded revision or fully deleted from Intraqual — both look identical to the anti-join, both get pruned). Runs unconditionally, not gated by `DRY_RUN` (that widget only protects source *files* on the volume, not derived index rows). Added 2026-07-27 after finding ~200 stale IDDOCs / ~3,400 stale chunks accumulated under the old REF-based gate.
- **Cluster policies**: none of the org's 6 "Job Compute *" policies fit this job's clusters (all force `SPOT_WITH_FALLBACK`, which would reintroduce a fixed spot-driver-reclaim incident on the single-node CPU clusters; none allow a GPU-ML `spark_version`). Deliberate exception, no `policy_id` set — see the `databricks-job-conventions` skill for the audited policy list before revisiting.
- **`run_as`** (`job-runner-sa-uat`, `3e5cd4e5-f765-4760-b974-ee7715258b39`) — as of 2026-08-19, enabled and confirmed working end to end on: `parsing_pipeline` (`qualibot-uat` only — it isn't deployed on `qualibot-uat-test`, see the job's own YAML), `lakebase_export_uat_to_volume`, `apps_stop_nightly_uat`/`qualibot_stop_weekend_uat`/`qualibot_start_weekend_uat` (needed an explicit `CAN_MANAGE` app-permission grant, done 2026-08-19), and `migrate_lakebase_uat_test`/`sync_user_capabilities_uat_test`. The earlier Lakebase-Postgres-role blocker (`password authentication failed`) is resolved. Still blocked: `sync_user_capabilities_uat` — needs `USE SCHEMA`+`SELECT` on `system.access` (metastore admin action). Not usable in the `dev` target — this SP is UAT-workspace scoped; a `run_as` set there is silently ignored (job runs as the submitting user instead of erroring), confirmed live 2026-08-19.
