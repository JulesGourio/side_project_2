## Code conventions (since 2026-10-08)

- **Comments**: only the non-obvious *why*, in one or two lines. No incident story, no date, no document or ticket name (the story goes in a README, the rule stays in the code), no paraphrase of the code, no commented-out code.
  **The code stands alone.** No comment, docstring, log or error message narrates a change or a fix ("before X, now Y", "fixed", "no longer", "added after the review", "regression", "used to"), refers to a pull request, a reviewer, a bug, an incident, a run, a runbook or any file of `runbooks/`, or says where a step is documented. When a behaviour changed, the comment (if the behaviour is not obvious) describes the behaviour as it is now, as a present-tense rule, never the difference with the past. History belongs in git, not in the code.
- **Docstrings and types**: every function and method, nested ones and notebook functions included, has a Sphinx docstring (a one-line summary, then `:param name:` for each parameter and `:return:` when it returns a value) and a return annotation. A docstring states the contract (what each parameter and the result mean: unit, format, what `None` means), not how the body works, so it sits alongside the short-comments rule above and does not replace it: inside a function only the non-obvious *why* gets a comment. `python3 runbooks/scripts/code_quality/check_docstrings.py server utils` must report 0 problems. Types are written `X | None` (never `Optional`), imports of the application are absolute (`from server.…`).
- **Logging**: `logger` in notebooks and modules, never `print`; CLI scripts under `utils/` follow the same rule.
- **Notebooks** (`utils/parsing_pipeline/`) follow the notebook layout of the reference repository (`archives/qualibot_archi.zip` in `JulesGourio/datab`, the notebooks under `proj/` and `data_asset/`): header cell, `Technical debt` (only concrete debt, one line each), `Configuration` (`Config Standard Package Imports`, `Config Function Imports`, `Config Widgets`, `Config logger`), `Inputs`, `Data Preparation` (`Prep N`), `Data Transformations` (`Tr. N`), `Quality Checks`, `Outputs`; a markdown cell with the *why* before each block; no `DBTITLE`, no hardcoded environment (`dev`/`uat`/`prod`) in a path default. Widgets are snake_case. The environments are widgets, declared first in `# Configuration` (before the imports, so `config` sees them): `pipeline_write_env` (the tables are written to `{pipeline_write_env}_proj.qualibot.<table>`), `pipeline_read_env` (tables another task of the job wrote; empty means `pipeline_write_env`), `reference_read_env` (reference data, `prod` in every target), `bypass_quality_checks` (RED checks logged as AMBER) and `debug`, with `log_level`. The job passes the three environments as base parameters of every notebook task; the notebook copies them to the environment that `config` reads on import, after any `restartPython()`. A notebook never falls back on a default environment. The run-time choices (`run_mode`, `parse_filter`, `max_parse_files`, `max_source_staleness_hours`, `redescribe_all_images`) are job parameters of the parsing job: changed per run, defaults in `resources/parsing_pipeline.job.yml`. Table and volume paths are built from the environments; the other values are constants of `config.py`. Quality checks go through Great Expectations, imposed by the organisation (`tables.py` → `leap_utils` `gx_validation`), grouped in `# Quality Checks`; GX is not available on serverless, so `6_update_kb_metadata` checks in Python (`check_rows`). GX comes from the S policy on the CPU clusters (`great-expectations~=0.18.0`); the GPU cluster (no policy) declares `great_expectations==0.18.22` on the `3b_parse_pdf` task. Every notebook calls `quality.require_gx()` in its import cell: a UAT `3_parse` without GX died at its quality checks after 20 h of parsing (2026-10-16). Any library a task needs late is installed on that task and imported in its first cells. `leap_utils/` (repository root, a copy of the shared library) provides the table writes, merges and GX helpers (`save_table`, `merge_into`, `gx_validation`); its freshness pilot write is off in this repository (`FRESHNESS_PILOT_ENABLED` in `leap_utils/data_asset/table_utils.py`).
  Names: the six parsing notebooks are `create_proj_<asset>.py` (`create_proj_category_reference`, `create_proj_parse_manifest`, `create_proj_parsing_checkpoint` (+ `_gpu`), `create_proj_chunks`, `create_proj_image_metadata`, `create_proj_doc_catalog`) and `update_proj_vector_indexes.py` (no table to create), without numbers: the order lives in the job YAML task chain (`1_categories` -> `6_update_kb_metadata`). Their header is `# PROJ <ASSET>`. The reference repository (`JulesGourio/datab`, `archives/qualibot_archi.zip`) is the answer to any question on naming or layout; leave it untouched.
  Scope: the section layout applies to the parsing pipeline only. The job notebooks (`utils/evaluation`, `utils/lakebase_sync`, `utils/app_mgmt`) keep the Databricks source header, the logger and no `print`; their table writes stay on `spark` until a Databricks run validates `leap_utils` in their job environments. One-shot notebooks in `runbooks/scripts/` are exempt.
- **Layout of `utils/`**: one folder per concern, map in `utils/README.md`. **Layout of `server/`**: `services/{chat,compare,infra}/` (chat engine and its LLM/logging/translation; compare processors and tools; shared Lakebase / user / Vector Search / catalog / streaming), prompts as files in `server/prompts/chat/`, map in `README.md` ("Server layout"). A chatbot prompt is never a string in Python.
- After a refactor that touches paths or notebooks, add what to re-run to `runbooks/retest.md`.

## Parsing pipeline (`utils/parsing_pipeline/`, `resources/parsing_pipeline.job.yml`)

Daily chain: `1_categories` -> `2_manifest` -> `3_parse` (CPU: scope, selection, resume, every non-PDF format and up to `GPU_MIN_PDFS` (30) PDFs) -> `3b_needs_gpu` (condition) -> `3b_parse_pdf` (GPU, only above 30 PDFs) -> `3c_chunks` (CPU: retry, chunks, GX, writes; depends on the `false` outcome of the condition or on `3b_parse_pdf`, `run_if: AT_LEAST_ONE_SUCCESS`) -> `4_describe_images` (LLM) -> `5_sync_index`. The parse tasks hand over through `parsing_run_scope` and `parsing_gpu_queue` (rewritten every run, hence `max_concurrent_runs: 1`). Only PDFs use Docling's GPU models; a daily run (0 to a few PDFs) never starts the GPU cluster. Redesign in progress: `runbooks/parsing_refonte.md`. Schedule exists on all targets but is `PAUSED` until explicitly promoted.

- **Metadata source** (since 2026-10-21): the tables of the Intraqual data asset, `prod_gold.quality_system.document_revisions_intraqual` (one row per IDDOC = `document_revision_ID`, with main category, `category_ID_path`, `document_type`, `published_date`) and `category_ancestors_intraqual` (category names), built as `{REFERENCE_READ_ENV}_gold.quality_system` (job variable `reference_read_env`, widget `reference_read_env`, `config.INTRAQUAL_GOLD_CATALOG_SCHEMA`), instead of `prod_bronze.intraqual.gd_*_latest`. The outputs of the pipeline do not change. The data asset's own notebooks and job YAML (copy of `leap-dbx-repository`, which owns them) are in `runbooks/leap_dbx_repository/`: never cite that folder in the READMEs, the code or the bundles. `1_categories` fails the run if one of the two tables was last written more than `PARSING_MAX_SOURCE_STALENESS_HOURS` ago (`DESCRIBE DETAIL`). Business names come from the header dictionary `prod_bronze.headers_others.headers_intraqual_gd_doc` (`iddoc` -> `document_revision_ID`, `ref` -> `document_reference`, `titre` -> `document_title`, `indice` -> `document_index`, `courant` -> `revision_status_code`, `etat` -> `lifecycle_state_code`, `nonvisible` -> `is_hidden`, `dtdiff` -> `published_date`).

Job YAML/notebooks keep a one-line pointer only — see the `databricks-job-conventions` skill for the org-wide version of this rule.

## Operational conventions (for Claude, not for the repository documentation)

These rules are for whoever changes the code. They do not belong in the READMEs or in the code comments.

- Notebooks under `utils/` (`*_job.py`, `ensure_*`, `import_*`, `grant_*`, `stop_start_app_job.py`, `evaluation/*.py` marked `# Databricks notebook source`) do not run from the command line. They are job tasks or notebooks opened in Databricks.
- Logging uses `logger` (the `logging` module), never `print`. Notebooks and command-line scripts follow the same rule.
- A notebook that takes parameters declares them as widgets, after `dbutils.widgets.removeAll()`.
- Notebooks import `ops_config.py` after adding `utils/` to `sys.path`: `sys.path.insert(0, os.path.dirname(os.getcwd()))` in notebooks (their folder is on `sys.path`, its parent is `utils/`), `Path(__file__).resolve().parent.parent` in command-line scripts.
- On data columns, `try_cast` and `try_to_date` replace `cast` and `to_date`, so one malformed value does not fail the whole task.
- `target_env.json` is the single source of the application settings per target. The PowerShell deploy script and the Bitbucket pipeline both read it: never copy its values elsewhere.
- Application start and stop (`app_mgmt/stop_start_app_job.py`): the SDK raises `BadRequest` when the application is already in the requested state. The notebook reads the state first and skips the call when it is already there.
- Line endings of the rendered `target_config.env`: `render_target_config_env.py` writes LF. A CRLF file adds a `\r` to every value, and every URL built from those values becomes wrong.
- A notebook imported into the workspace: `databricks workspace import` must target exactly the job's `notebook_path` (without the `.py` suffix), otherwise a duplicate appears without an error.
- Deployment: the application is deployed with `utils/deploy/deploy_qualibot.ps1` (or the Bitbucket pipeline), the jobs with `databricks bundle deploy`. The root README describes the targets.
- Job format: every job sets `queue`, `email_notifications` on `on_failure` with `${var.notification_email}`, `notification_settings.no_alert_for_canceled_runs`, and the tags `activity-type` (`${var.job_activity_tag}`), `job-purpose` and `project-name`. The template is `datab/templates/bundle_data_asset/`.
- `CAN_QUERY` is never granted on serving endpoints: every workspace user already queries them (`CLAUDE.md`, Databricks section).
- READMEs never mention `runbooks/` (no link, no index, no sentence pointing to the steps): the folder is temporary in this repository. Inside `runbooks/` itself, the usage commands keep the script paths, and `runbooks/README.md` is that folder's own index.
