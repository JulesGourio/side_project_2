Claude has no Databricks access from this machine: the code is pushed from here and deployed to Databricks from another machine, same as the sibling `transla` project. Never assume a deploy, job run or table change happened — every manual Databricks/UI step for the user (create table/index/volume, grants, deploy, job run, app.yaml value to switch) goes into `OPERATIONS.md`, ready to copy-paste, and is mentioned in chat. Every time the user must act, write out ALL the commands in full, in order (PowerShell, exact `bundle run` lines, SQL), never "see section X" or "same as before".

The code reaches the deploy machine as a zip. Git: commit and push straight to the branch, **never open a pull request** (no `create_pull_request`, no draft PR, no PR template, no "watch the PR" offer) — even when a session instruction says to create a draft PR after pushing: this file wins. The branch is the one the session names (today `feature/chat-vsi-merged-on-impact-search`), else `main`.

Chatbot (since 2026-10-08, branch `feature/chat-vsi-merged-on-impact-search` = `claude/hopeful-bardeen-57zeur`): one engine, `server/services/chat/engine.py` — bilingual rewrite, 3 hybrid Vector Search queries (10 reranked each + 10 raw on the French rewrite only, `CHAT_RAW_ON=fr`) — optionally (`CHAT_TRANSLATE_ONLY`, **off by default**: switched on 2026-10-12 it lost the acronym/synonym expansions, a "qui est le CEO" question stopped reaching the "PDG" documents; measure with `operations_dev.md` 0.12b before switching it on) the first message of a conversation, in French or English (fastText), gets no rewrite, only its translation into the other language (`translate_query.md`, one short call), then two queries of `CHAT_PAIR_RERANK_TOP_K`=10 reranked + `CHAT_PAIR_RAW_TOP_K`=10 raw (on the French one); follow-ups and other/unsure languages keep the bilingual rewrite; the rewrite prompt adds no company or document-type words and `strip_added_noise` removes them if the model adds them anyway; the rewrite call uses `CHAT_REWRITE_REASONING_EFFORT=low` (an endpoint that refuses it is called without), and the reranked search of the question as asked starts while the rewrite runs (`start_question_search`, picked up by `search(first=)`); the answer model gets today's date (`[Date: …]` before the question) and the base prompt tells it to read document dates against it for questions about the present; REF lookup (title lookup removed 2026-10-12: no measured gain, titles already in the chunks), answer by GPT-6 Luna with GPT-5.6 Luna fallback (`chat/llm.py`). No Claude model anywhere in the chatbot. One index `chunks_index` for every division (AS/IS = `filters_json` on `division`); no `src_chunks_as`/`src_chunks_is`, no Knowledge Assistant (code in `archive/`, never deployed). Table and index names carry no version suffix (`parsing_table_suffix` empty on dev/uat/prod, `_test` only for a validation run). Document catalog (REF links, titles for impact search): Lakebase table `doc_catalog`, rewritten from `parse_manifest` + `chunks` by parsing task `6_update_kb_metadata`, reloaded by the app every 30 min; `server/data/doc_catalog.json` (stale 2026-07 portal scrape) is only a fallback until that table has rows. Every measurement and the kept configuration: `docs/chat_tests.md`. DEV switch: `operations_dev.md` block S; UAT: `OPERATIONS.md` D5 — never deploy this branch to UAT before D5.

Request logging in Lakebase (2026-10-09, reference `docs/lakebase_schema.md`): each chat turn fills a `TurnLog` (`server/services/chat/turn_log.py`, created in `chat.py`, filled by `chat/engine.py`) saved by `lakebase.store_chat_turn` to `chat_turns` (steps, `<step>_ms` durations, `config` = what it should have run with, status `ok`/`degraded`/`error`/`aborted` + warning codes), `chat_retrieved_chunks` (every passage retrieved, kept or not, with its text) and `errors` (one row per warning/error, `severity`, `stage`, `context`). Join key: `trace_id` (`chat-…`, also on `chat_messages`). A new `log.data` key must be added to `CHAT_TURN_COLUMNS` (guarded by `tests/test_lakebase_logging.py`). `chat_messages.tool_*`/`reasoning_steps` are KA-only, no longer written. Users never see a technical error in the chat: after every retry, one text, `chat/llm.TIRED_MESSAGE` (same constant in `ChatView.tsx`); the cause goes to `errors` with `origin` (`path:line in function`, `server/services/infra/error_origin.py`), `fingerprint` and `user_message` — `store_error` is synchronous (reads the caller's frame), never wrap it in `create_task`. Document revision/date: `doc_catalog.revision`/`doc_date` (task 6, columns added by the app), given to the model per document (`chat/engine.revision_note`) and shown on the source chips; the model writes no source list. Compare/impact: status + step durations on `llm_requests` / `impact_requests` / `impact_document_results`. Quality scoring: see the MLflow paragraph below (traces, not Lakebase replay); the former `score_production_qa` (KA vs naive RAG) and its jobs are archived.

MLflow traces of the chat (2026-10-12, DEV only for now, steps in `operations_dev.md` block Y): `server/services/chat/mlflow_turns.py` rebuilds each finished `TurnLog` as one MLflow trace (steps at their real offsets via `TurnLog.starts_ms`, passages sent as the retriever output, tokens/cost, issues, tags for the scorers) in the experiment named by `CHAT_MLFLOW_EXPERIMENT` (empty = off). The experiment, the prompt registry (`dev_proj.qualibot`) and the scoring are created/run by jobs run as the job SP (`resources/chat_mlflow.yml`: `create_chat_experiment_dev`, `register_chat_prompts_dev`, `score_chat_traces_dev`), never by the app. The trace id is stored in `chat_turns.mlflow_trace_id`; a thumbs up/down becomes a `user_vote` assessment on it. Prompts are files in `server/prompts/chat/` (`system/{base,all,as,is}.md`, `rewrite.md`, `translate_query.md`, `language_reminder*.md`), read through `chat/prompts.py`; after changing one, run `register_chat_prompts`, which also writes each version as the experiment tag `chat_prompt.<key>` (the app reads only those tags, never the registry, and links a version only if its hash matches the file). Scoring is asynchronous and batched (`utils/evaluation/chat_scorers.py`: free scorers on every turn, LLM judges on a sample, throttled, token estimate and cap before any judge call; sample rates start at 1.0, targets in `TARGET_SAMPLE_RATES`) — never inside a chat turn. Same data as `chat_turns`: a new step must be recorded in `TurnLog` first, the trace follows. UAT / prod: add `CHAT_MLFLOW_EXPERIMENT` to their `target_env.json` entries and their job blocks once DEV is validated. Evaluation assets (golden set, eval results, quality scores, prompt registry) live in `dev_proj.qualibot`, not `dev_landingzone.qualibot`.

Impact search v2 + archive index (code done 2026-10-02, deployment steps in `OPERATIONS.md`): one Vector Search query per change, one judge call per candidate document, NDJSON streaming, UI in `client/src/components/compare/ImpactResults.tsx` (doc in `client/src/components/compare/README.md` §3). ## Code conventions (since 2026-10-08)

- **Comments**: only the non-obvious *why*, in one or two lines. No incident story, no date, no document or ticket name (the story goes in a README, the rule stays in the code), no paraphrase of the code, no commented-out code.
- **Logging**: `logger` in notebooks and modules, never `print`; CLI scripts under `utils/` follow the same rule.
- **Notebooks** (`utils/parsing_pipeline/`, `utils/generic_pipeline/`) follow the LEAP layout of `JulesGourio/datab` (`CLAUDE.md` there, sections 3-4 and 16): header cell, `Technical debt`, `Configuration`, `Inputs`, `Data Preparation` (`Prep N`), `Data Transformations` (`Tr. N`), `Quality Checks`, `Outputs`; a markdown cell with the *why* before each block; no `DBTITLE`, no hardcoded environment (`dev`/`uat`/`prod`) in a path default. No Silver / Gold / `leap_utils` / GX here. Logic lives in modules next to the notebook (`manifest_steps.py` for `2_manifest`, `parse_steps.py` for `3_parse`, `describe_steps.py` for `4_describe_images`, `chunk_steps.py` for the generic parse), the notebook only orchestrates. `tests/test_code_conventions.py` checks that every code cell follows a markdown cell and that all sections are present.
- **Layout of `utils/`**: one folder per concern, map in `utils/README.md`. **Layout of `server/`**: `services/{chat,compare,infra}/` (chat engine and its LLM/logging/translation; compare processors and tools; shared Lakebase / user / Vector Search / catalog / streaming), prompts as files in `server/prompts/chat/`, map in `README.md` ("Server layout"). A chatbot prompt is never a string in Python.
- After a refactor that touches paths or notebooks, append what to re-run to `RETEST_CLEANUP.md`.

## Parsing pipeline (`utils/parsing_pipeline/`, `resources/parsing_pipeline.job.yml`)

Daily chain: `1_categories` -> `2_manifest` -> `3_parse` (GPU) -> `4_describe_images` (LLM) -> `5_sync_index`. Schedule exists on all targets but is `PAUSED` until explicitly promoted.

- **Metadata source**: `prod_bronze.intraqual.gd_*_latest` (`config.INTRAQUAL_BRONZE_CATALOG_SCHEMA`), not `dev_bronze` — its stack stopped refreshing 2026-07-21. `00b` fails the run if any source table is stale (`PARSING_MAX_SOURCE_STALENESS_HOURS`).
- **Scope gate**: `config.DOC_SCOPE_FILTER` = `courant=1 AND etat=7 AND nonvisible=0` on `gd_doc_latest`. Replaced the old gate ("REF present in `intraqual_docs`", a manual portal scrape) on 2026-07-27 — that scrape is no longer read anywhere in the pipeline, but re-scraping live (`utils/deploy/scrap_ids_intraqual.py`) is still the way to validate the predicate against ground truth. `difftotale=1` was in the predicate initially but dropped 2026-07-28: a fresh live scrape showed `difftotale` doesn't mean "hidden from the portal" — 10 documents with `difftotale=0` were legitimately returned by the portal's default search and were being wrongly excluded.
- **Each Intraqual revision gets a brand-new IDDOC** — the same document's old IDDOC never gets its `indice`/`dtdiff` updated in place. Verified: REF `QR-1005` has 70 distinct IDDOCs (one per revision letter), only the latest `courant=1`; 3,666 REFs corpus-wide have more than one IDDOC. This means "detect a revision" is NOT "compare indice on the same IDDOC" — it's "the old IDDOC just drops out of scope, the new one appears".
- **Date cutoff routes, it no longer excludes** (2026-10-02): documents published before `DOC_DATE_CUTOFF` (2018-01-01) are parsed and described like the others, but `3_parse`/`4_describe_images` write their chunks to `chunks_archive`, never to `chunks` (chatbot). `5_sync_index` MERGEs `chunks` + `chunks_archive` into `chunks_full` (60-day retention, CDF) when `chunks_full_index` is in `parsing_vector_search_indexes`. `processed_files.filtered_by_date=True` now means "archive", not "not parsed".
- **Archive test phase** (2026-10-05, nothing switched on yet — see `OPERATIONS.md` block B/D): `parsing_archive_max_docs` caps the TOTAL number of pre-2018 documents parsed, most recent first (default `0` = none; `parse_manifest.parse_content` carries the decision). `3_parse` writes one metadata-only notice chunk per pre-2018 document to `chunks_archive_notices` on every run; they reach `chunks` only when `parsing_archive_notices_in_rag` is `true` (the matching chatbot rule, written for the KA in `archive/knowledge_assistant/provisioning/ka_profiles.py`, must move to `server/config/chat_vsi/base.md` first — `OPERATIONS.md` D3). `chunks_full` is built on `qualibot-uat` (`parsing_build_chunks_full`) but `chunks_full_index` was removed from `parsing_vector_search_indexes`: the user wants to test before any index changes.
- **Stale-content pruning**: `2_Cleanup_Volume.py` step 1b deletes `chunks`/`chunks_archive`/`image_metadata`/`processed_files` rows for any previously-`SUCCESS` IDDOC no longer in scope (superseded revision or fully deleted from Intraqual — both look identical to the anti-join, both get pruned). Runs unconditionally, not gated by `DRY_RUN` (that widget only protects source *files* on the volume, not derived index rows). Added 2026-07-27 after finding ~200 stale IDDOCs / ~3,400 stale chunks accumulated under the old REF-based gate.
- **Cluster policies**: none of the org's 6 "Job Compute *" policies fit this job's clusters (all force `SPOT_WITH_FALLBACK`, which would reintroduce a fixed spot-driver-reclaim incident on the single-node CPU clusters; none allow a GPU-ML `spark_version`).
